## ร่าง A — สั้น (สำหรับฟีด · สามบรรทัดแรกต้องเอาอยู่)

> เขียน UI ด้วย AI แล้วมันจะโปะคำอธิบายทับสิ่งที่จอบอกอยู่แล้วเสมอ
>
> tooltip บนเซลล์สีเหลืองในตารางลงเวลา AI เขียนมาว่า
> `ระบบตัดเวลาให้ที่ 8 ชม. — ไม่ได้กดหยุดเอง`
>
> ที่ถูกคือ `ตัดเวลาที่ 8 ชม.`
> เพราะเซลล์มันเหลืองอยู่แล้ว สีพูดส่วนที่เหลือไปแล้ว
>
> ทำ Skill ของ Claude Code ไว้ตัวหนึ่ง ชื่อ Klao (เกลา) กฎทุกข้อกลั่นจากงานที่ merge แล้วจริง
> ไม่ใช่รายการคำแปลจากอังกฤษ เน้นหนักที่สตริง UI ซึ่งฝั่ง humanizer สายบทความยังไม่ค่อยแตะ
>
> อีกสี่ตัวอย่าง
> `— ทีม —` (placeholder ใน select) → `เลือกทีม`
> `{roleLabel ?? '—'}` → `{roleLabel ?? 'ไม่ระบุ'}`
> `บันทึกไม่ได้ — X กำลังแก้ไข` → `X กำลังแก้ไขอยู่ บันทึกไม่ได้`
> `อีเมลของคุณเปลี่ยนแล้ว` → `อีเมลเปลี่ยนแล้ว`
>
> ครึ่งที่ผมคิดว่าสำคัญกว่ากฎ คือรายการ **ของที่ห้ามแก้** 28 ข้อ ที่ชนะไฟล์กฎทุกไฟล์
> เช่น em-dash ในภาษาอังกฤษถูกอยู่แล้ว · `08:00–20:00` ถูกอยู่แล้ว · `8 ชม.` `พ.ศ.` ถูกอยู่แล้ว
> · และคำซ้ำบางตัวห้ามหาคำพ้องความมาสลับ เพราะมันเป็นโซ่ที่ยึดโครงประโยคไว้
>
> MIT · github.com/SeedGrit/klao

## ร่าง B — ยาว (สำหรับคนที่อ่านจบ · โพสต์เดี่ยวหรือ note)

> **ทำไมข้อความที่ AI เขียนใน UI มันอ่านออกว่าใครเขียน**
>
> ไม่ใช่เพราะคำศัพท์ เป็นเพราะมันอธิบายซ้ำสิ่งที่จอบอกอยู่แล้ว
>
> ปีนี้ผมเกลาคำในแอปไทยไปหลายสิบจุด แล้วเอาสิ่งที่ตัดออกมาทำเป็น Skill ของ Claude Code
> ชื่อ Klao (เกลา) กฎทุกข้อมาจาก diff ที่ merge แล้วจริง ไม่ได้คิดขึ้นเอง และหลายข้อมาจากรอบที่
> **ผมเกลาเอง** แล้วเอามาเทียบกับรอบที่ AI เกลา — ซึ่งผลออกมาไม่เหมือนกันอย่างมีแบบแผน
>
> ▍1 · ตัดหางที่จอบอกอยู่แล้ว
>
> `ระบบตัดเวลาให้ที่ 8 ชม. — ไม่ได้กดหยุดเอง` → `ตัดเวลาที่ 8 ชม.`
> เป็น tooltip บนเซลล์สีเหลือง สีของเซลล์พูดส่วนที่เหลือไปแล้ว
>
> `เพิ่มปฏิทินแล้ว — กำลัง sync รอบแรก` → `เพิ่มปฏิทินแล้ว กำลัง sync`
> `รอบแรก` ไม่ได้ให้ข้อมูลกับคนที่เพิ่งกดเพิ่ม
>
> `ยังไม่มีอุปกรณ์ที่เปิดแจ้งเตือน — เปิดด้านบนก่อน ไม่งั้นตั้งไว้ก็ไม่มีอะไรมา`
> → `ยังไม่มีอุปกรณ์ที่เปิดแจ้งเตือน เปิดด้านบนก่อน`
> หางเป็นการหยอด
>
> ▍2 · ขีดเปล่าที่ยืนแทนค่าว่าง อ่านไม่ออกว่าหมายถึงอะไร
>
> `{roleLabel ?? '—'}` → `{roleLabel ?? 'ไม่ระบุ'}`
> `แก้ไขล่าสุดโดย {name ?? '—'}` → ไม่ต้อง render บรรทัดนั้นเลยเมื่อไม่มีชื่อ
>
> สี่ทางเลือก เรียงตามลำดับที่ควรลอง คือ ไม่แสดงบรรทัดนั้น → เว้นว่าง (ในตาราง) →
> คำที่บอกว่าทำไมถึงว่าง (`ไม่พบสมาชิก`) → คำกลาง ๆ (`ไม่ระบุ`)
>
> ▍3 · เอาข้อสรุปขึ้นก่อน
>
> `บันทึกไม่ได้ — X กำลังแก้ไข` → `X กำลังแก้ไขอยู่ บันทึกไม่ได้`
> `ครบ 8 ชม. ของวันนี้แล้ว — เริ่มจับเวลาใหม่ไม่ได้` → `วันนี้ครบ 8 ชม. แล้ว เริ่มจับเวลาใหม่ไม่ได้`
>
> ▍4 · บทความยาวมีด่านคนละด่านกับ UI
>
> ในเนื้อหาไทยที่ AI ร่าง 828,000 อักขระ เจอ em-dash 2 ครั้ง
> แต่เจอมหัพภาคท้ายประโยคไทย 1,134 ครั้ง
>
> `แล้วทุกอย่างจะคลี่คลาย.` → `แล้วทุกอย่างจะคลี่คลาย` (1,134 → 0)
> `ค่อยๆ ดีขึ้น` → `ค่อย ๆ ดีขึ้น` (413 → 78)
> `ใบเซียมซีหมายเลข 9 นี้` → `ใบเซียมซีหมายเลขเก้านี้` (77 → 4)
>
> ด่าน em-dash เป็นด่านของสตริง UI ไม่ใช่ของบทความ เอาไปใช้สลับกันแล้วจะได้ 0 แล้วเข้าใจว่าผ่าน
>
> ▍5 · อุปมาที่ผู้อ่านต้องถอดรหัส รวมอุปมาที่ AI คิดขึ้นเองด้วย
>
> `ตำราที่แข็ง / ตำราที่หลวม` → `ตำราที่ระบุชัด / ตำราที่กล่าวแค่ภาพรวม`
> `คนอ่านแบกน้ำหนักเอง` → `คนอ่านรับภาระในการตีความเอง`
> `ช่วงเวลามีรสของมัน` → `ช่วงเวลามีลักษณะของตัวเอง`
> `แผนที่ความกังวลของมนุษย์` → `บันทึกความกังวลของมนุษย์`
> `เครื่องสามชิ้น` → `องค์ประกอบ 3 อย่าง`
>
> ห้าตัวนี้ผมตัดในบทความเดียว และ **AI คิดขึ้นเองสด ๆ ทั้งห้าตัว** ไม่ได้ยืมจากอังกฤษสักตัว
> (ในบทความเดียวกันมีที่ยืมมาจริงอยู่ตัวเดียว) — เกณฑ์จึงไม่ใช่ *ยืมมาหรือเปล่า* แต่เป็น
> *ผู้อ่านต้องแปลอีกชั้นไหม* อุปมาที่ไม่มีใครเคยได้ยินมาก่อนยิ่งแพงกว่า
>
> แถวที่สองมีบทเรียนซ้อน ของเดิมบอกว่า*มี*ภาระ ของใหม่บอกว่า**ภาระคืออะไร**
>
> อุปมาที่ผ่านในบทความเดียวกัน เก็บไว้เป็นเส้นเทียบ: `ราก` `กิ่ง` `ลำต้น` เพราะไทยมี รากเหง้า ·
> ต้นตระกูล · แตกกิ่งก้านสาขา อยู่ก่อนแล้ว
>
> ▍6 · ครึ่งที่ผมว่าสำคัญกว่าตัวกฎ คือรายการของที่ห้ามแก้
>
> `references/false-positives.md` มี 28 ข้อ และชนะไฟล์กฎทุกไฟล์ ทุกข้อมีบรรทัด
> "เป็น tell จริงเมื่อ" ที่บอกว่าข้อยกเว้นสิ้นสุดตรงไหน
>
> em-dash ใน prose อังกฤษถูกอยู่แล้ว และอาจเป็นลายเซ็นคนเขียน
> `08:00–20:00` `จ–ศ` ถูกอยู่แล้ว
> `8 ชม.` `พ.ศ.` `20.00 น.` ถูกอยู่แล้ว (grep ติดหมด แต่เป็นอักษรย่อ)
> `แก้ UI ราว 50 จุด` `709 บรรทัด` — ตัวเลขวัดจริงคือของดี ไม่ใช่ความยาวเกิน
> `const label = "ยืนยัน"` — `"` คร่อม string ในโค้ด แก้แล้วโค้ดพัง
>
> และข้อที่ผมชอบที่สุด คือคำซ้ำที่ห้ามหาคำพ้องความมาสลับ
>
> `ทุกระบบต้องมีขอบเขตจำกัด เพราะตำราคือการบีบชีวิตที่ไม่มีขอบให้ลงตารางที่มีขอบ`
> → `ทุกระบบต้องมีขอบ เพราะตำราคือการบีบชีวิตที่ไม่มีขอบให้ลงตารางที่มีขอบ`
>
> `ขอบ` สามตัวในประโยคเดียวอ่านเหมือนความบกพร่อง แต่เป็นโซ่ที่มัดข้ออ้างเข้ากับเหตุผล
> เปลี่ยนตัวแรกเป็นคำพ้องความแล้วโซ่ขาด
>
> ▍7 · กฎหลายข้อกลับทิศตามชนิดของงาน
>
> ในเนื้อหาที่ทำนายอนาคตให้ผู้อ่าน Skill ต้อง **เพิ่ม** hedge ไม่ใช่ตัด
> `จะสำเร็จ` → `มีเกณฑ์สำเร็จ` · `ต้อง` → `ควร`
>
> ในเอกสารยื่นลูกค้า คำตอบที่ถูกคือ **ขยาย** ประโยคให้เป็นทางการเต็ม ไม่ใช่ย่อ
>
> heuristic "สั้นกว่า = คนกว่า" ถูกปิดทั้งข้อในสองกรณีนี้
>
> ▍จบงานได้อะไร
>
> ตาราง Before → After ทุกบรรทัดที่แก้ พร้อม rule ID ให้โต้แย้งได้ทีละแถว
> บวกย่อหน้า "จงใจไม่แตะ" ที่บอกว่าอะไรที่เห็นแล้วแต่ไม่แก้ และเพราะอะไร
>
> แถวที่อ้าง rule ID ไม่ได้ = ยังไม่มีกฎรองรับ ต้องถามก่อนแก้

# False positives — ของที่ดูเหมือน tell แต่ห้ามแก้

ไฟล์นี้ชนะ `tells-th.md` และ `tells-en.md` เสมอ ถ้ากฎข้อไหนขัดกับรายการที่นี่ ให้ยึดที่นี่

รูปแบบแต่ละรายการ: **pattern · ทำไมถึงโดน flag ผิด · เมื่อไหร่ถึงเป็น tell จริง**

pattern ที่ FP สูง (keep rate ≥ 70%) ห้ามแก้เงียบ ๆ — **เสนอทางเลือกพร้อมเหตุผลแล้วให้เจ้าของตัดสิน**

---

## 1. use-vs-mention — ข้อความที่กำลัง*พูดถึง* pattern

ข้อความใน backtick หรือ quote ที่ยกมาเป็นตัวอย่างของ pattern ไม่ได้*ใช้* pattern นั้น
สำคัญมากตอนเกลาไฟล์ style guide หรือ SKILL.md เอง

| ดูเหมือน | ที่จริงคือ |
|---|---|
| บรรทัด `` `ค่อยๆ` → `ค่อย ๆ` `` | กำลังสอนกฎ TH-OR-02 ไม่ใช่ละเมิดมัน |
| บรรทัด `` `ไม่ได้.*แต่` `` ใน grep | regex ไม่ใช่ประโยค |

**เป็น tell จริงเมื่อ:** ข้อความนั้นเป็นเนื้อหาที่ผู้อ่านต้องอ่านเอาความ ไม่ใช่ตัวอย่างที่ยกมา

## 2. `ยิ่ง…ยิ่ง…` ที่เป็นสำนวนแท้

`ยิ่งเร็วยิ่งดี` เป็นสำนวนไทย ไม่ใช่ของนำเข้า · คลังข้อมูลที่สี่: **0→10** คนเกลาสร้างขึ้นเองทั้งหมด
(อยู่ในอี้จิงทั้ง 10 จุด นับที่ระยะห่างไม่เกิน 25 อักขระ)

**เป็น tell จริงเมื่อ:** ใช้เป็นท่าปิดซ้ำแทบทุกย่อหน้า (TH-PR-02)

## 3. en-dash ในช่วง + `·` separator

`08:00–20:00` · `จ–ศ` · ช่วงวันที่ของงวด — ถูกแล้ว
`·` เป็นตัวคั่น label ไม่ใช่สำนวน

**เป็น tell จริงเมื่อ:** en-dash เชื่อม*คู่ความคิด* ไม่ใช่ช่วง (`จังหวะการรุก–รับ` → `การรุกและการถอย`)
· `·` เชื่อมประโยคเต็มใน prose ของ register `formal`

## 4. em-dash ใน prose อังกฤษ

ถูกต้องตามหลักภาษา และอาจเป็นลายเซ็นคนเขียน — กฎ em-dash ใช้กับ**สตริงไทยที่ผู้ใช้เห็น**เท่านั้น

**เป็น tell จริงเมื่อ:** อยู่ในสตริงไทย (TH-UI-01)

## 5. `ไม่ได้ / ไม่ใช่ X แต่ Y` เมื่อ contrast คือประเด็นจริง

คลังข้อมูลที่สี่: `ไม่ได้…แต่` 60→95 · `ไม่ใช่…แต่` 21→25 — คนเกลา*สร้าง*ท่านี้เอง
(`ความไม่รู้คือแต้มต่อ` → `ความไม่รู้ไม่ใช่ข้อเสีย`)

**เป็น tell จริงเมื่อ:** เป็นท่าเปิดซ้ำ ๆ ไม่ใช่ตอนที่การเทียบคือเนื้อหา (TH-PR-01)

## 6. `อย่างมาก` / `อย่างมีประสิทธิภาพ` ใน register ทางการ

native ไม่ใช่คำแปล · คลังข้อมูลที่สี่: `อย่างมาก` 15→20 อยู่รอด 73% · `อย่างมีประสิทธิภาพ`
3→24 อยู่รอด 100%

**เป็น tell จริงเมื่อ:** ซ้ำหลายครั้งในย่อหน้าเดียว

## 7. ครับ/ค่ะ ใน chat และบทพูด

ไม่ใช่ filler แต่เป็นโครงบังคับของ register `spoken` เช่นเดียวกับกริยาถ่อมตัว `ขอ…`
(ขอเล่า / ขอเน้น) และคำขอบคุณเปิด-ปิด

**เป็น tell จริงเมื่อ:** โผล่ในสตริง UI หรือ docs ที่ไม่ใช่บทสนทนา

## 8. ศัพท์เทคนิค / ชื่อแบรนด์ / ทับศัพท์ที่ทีมใช้

ห้าม "แปลกลับ" เป็นไทยจนไม่ตรงกับปุ่มในจอหรือคำที่ทีมพูดกัน

**เป็น tell จริงเมื่อ:** ไม่มี — ห้ามแก้ทุกกรณี เว้นแต่เจ้าของบอกว่าเปลี่ยนชื่อแล้ว

## 9. Tricolon เดี่ยว

สามชิ้นครั้งเดียวไม่ผิด · ปิดกฎทั้งข้อใน `spoken` (message discipline) และ `forecast`
(สัดส่วนลิสต์สามชิ้นเพิ่ม +87%/วรรค = จังหวะที่ตั้งใจ)

**เป็น tell จริงเมื่อ:** ทุกลิสต์ในเอกสารเป็นสามชิ้นเหมือนกันหมด (TH-PR-04)

## 10. `ซึ่ง` ใน technical / legal clause

เมื่อต้องการ antecedent ที่ชัดเจนตามกฎหมายหรือสเปก · คลังข้อมูลที่สี่ 246→339 อยู่รอด 80%

**เป็น tell จริงเมื่อ:** เกิน 1 ตัวในประโยคเดียว และ antecedent เป็นรูปธรรมพอจะใช้ `ที่` แทนได้

## 11. adverb บอกลักษณะ — ห้ามเหมารวมกับตัวเร่งระดับ

`อย่างต่อเนื่อง` · `อย่างมั่นคง` · `อย่างราบรื่น` · `อย่างเต็มที่` · `อย่างชัดเจน` แบกข้อมูลของตัวเอง

คนเกลาเก็บหรือเพิ่มสามคำ: `อย่างงดงาม` (22→20 อยู่รอด 82%) · `อย่างที่สุด` (5→4 อยู่รอด 80%) ·
`อย่างลึกซึ้ง` (11→46 อยู่รอด 73%) — ส่วน `อย่างแท้จริง` (16→34 อยู่รอด 50%) กับ
`อย่างสง่างาม` (8→6 อยู่รอด 38% · ×0.51/วรรค) ก้ำกึ่ง ยังคง soft แต่ไม่ใช่ของที่คลังข้อมูลคุ้มครอง

**เป็น tell จริงเมื่อ:** ซ้ำในย่อหน้าเดียว · ส่วนตัวเร่งความแน่นอน (`อย่างยิ่ง` `อย่างแน่นอน`
`เป็นอย่างยิ่ง` `อย่างยิ่งยวด`) อยู่รอดแค่ 0–5% นั่นคือของที่ตัดจริง (TH-PR-05)

## 12. กาวย่อหน้าบางตัวใน `forecast` — คำเชื่อมที่ยืนเป็นวรรคของตัวเอง

| pattern | คลังข้อมูลที่สี่ | keep |
|---|---|---|
| `อย่างไรก็ตาม` | 91 → 360 (×6.19/วรรค ในรอบเขียนใหม่) | 99% |
| `นอกจากนี้` | 23 → 35 | 74% |
| `ในที่สุด` | 24 → 27 | 83% |

**กฎนี้ปิดเฉพาะสามคำข้างบน ไม่ใช่ทั้งหมวด J** คำอื่นในหมวดเดียวกันถูกกวาดจริงในคลังข้อมูลเดียวกัน:
`อีกทั้ง` อยู่รอด 9% (1 จาก 11 เรคคอร์ด) · `ทั้งนี้` 1→0 · `ในขณะเดียวกัน` อยู่รอด 47% ซึ่งคือ
`soft` ทำงานตามนิยาม ("ตัดราวครึ่งหนึ่งของที่เจอ ไม่ใช่หมด") ไม่ใช่การหักล้าง

**เป็น tell จริงเมื่อ:** อยู่นอก register `forecast` · หรือเป็น `อีกทั้ง`/`ทั้งนี้` แม้ใน forecast

## 13. แถวของ K (TH-PR-11) ที่คลังข้อมูล `forecast` หักล้าง

| pattern | คลังข้อมูลที่สี่ | keep |
|---|---|---|
| `มีความ` + คุณศัพท์ | 763 → 945 | 88% |
| `ความสามารถในการ…` | 43 → 317 (×5.85/วรรค) | 95% |
| `ถือเป็น` | 125 → 130 | 92% |
| `ในเรื่องของ` / `ในส่วนของ` | 37 → 35 | 89% |
| `ไม่ว่าจะเป็น A, B หรือ C` | 28 → 39 | 64% |
| `ได้รับการ` + กริยา | 108 → 188 | 75% |

`ได้รับการ` เข้าเพราะเป็น **register-lift** ไม่ใช่ passive ที่ต้องแก้ (`ถูก` 423→342 · `โดน` 10→0)

**เป็น tell จริงเมื่อ:** อยู่ในสตริง UI ที่ต้องสั้น — ตัวเลขทั้งตารางมาจาก register `forecast`
ซึ่งไม่มีสตริง UI สักตัว (เรคคอร์ดสั้นสุด 61 อักขระ) ใน `ui` แถวเหล่านี้ยังใช้ได้ตามเดิม

## 14. `นำทาง` / `เก็บเกี่ยว` ในเนื้อหาเชิงเปรียบ

`ปัญญานำทางชีวิต` · `เก็บเกี่ยวประสบการณ์` เป็นภาพพจน์ประจำ register ไม่ใช่ศัพท์ AI นำเข้า
· คลังข้อมูลที่สี่: `นำทาง` 61→70 อยู่รอด 88% · `เก็บเกี่ยว` 20→18 อยู่รอด 83%

**เป็น tell จริงเมื่อ:** ใช้เชิงนามธรรมในงานธุรกิจ/เทคนิค (`นำทางความเปลี่ยนแปลง` = navigate)

## 15. `เปรียบเสมือน` / `ดั่ง` — อุปมาที่เป็นโครงของ register

351→399 อยู่รอด 99% · `ดั่ง` 78→87 อยู่รอด 85% — อ่านเหมือนของประดับ แต่เป็นโครงเนื้อหา

**เป็น tell จริงเมื่อ:** อยู่ใน register `ui` หรือ docs เทคนิค ที่อุปมาไม่ได้ทำงาน

## 16. `ขอให้…` คำอวยพรปิดท้าย

235→215 อยู่รอด 91% · ตรงกับทั้ง TH-PR-03 (closer) และ TH-UI-08 (คำหยอด) แต่ใน `forecast`
กับ `spoken` เป็นข้อบังคับของรูปแบบ

**เป็น tell จริงเมื่อ:** อยู่ใน `ui` หรือ `prose` (toast ที่ลงท้ายว่า `ขอให้โชคดี` = ตัด)

## 17. `ค่อนข้าง` — H8 (TH-PR-08) ระบุชื่อไว้ แต่คลังข้อมูลไม่เห็นด้วย

33→40 อยู่รอด 85% · token เดียวในกลุ่ม hedge ที่คลังข้อมูลเห็นด้วยกับ H8 คือ `อาจจะ`
(34→27) ซึ่งเดินสวนทางกับ `อาจ` เดี่ยว (490→1,304)

**เป็น tell จริงเมื่อ:** ซ้อนกับ hedge ตัวอื่นในประโยคเดียว (`อาจจะค่อนข้าง…`)

## 18. `เสมอ` ที่จริงคือ `สม่ำเสมอ`

grep `เสมอ` ติด `สม่ำเสมอ` 97 จาก 247 ครั้ง (39%) ซึ่งเป็นคนละคำและไม่ใช่ lazy extreme
ถ้าจะ grep ต้องใช้ `(?<!สม่ำ)เสมอ` (150→160 อยู่รอด 62%)

**เป็น tell จริงเมื่อ:** เป็นคำเปล่าที่เคลมว่า "ทุกครั้งไม่มีข้อยกเว้น" โดยไม่มีหลักฐาน

## 19. `สิ่งที่…` — H7 (TH-PR-07) ระบุชื่อไว้

541→1,022 อยู่รอด 91% (×1.50/วรรค) · เป็น nominalization ที่ register นี้ใช้เป็นปกติ

**เป็น tell จริงเมื่อ:** แทนด้วยคำนามตรง ๆ ได้โดยความหมายไม่ขยับ (`สิ่งที่เขาทำ` → `งานของเขา`)

## 20. อักษรย่อไทยที่ใช้จุดถูกต้อง

`8 ชม.` · `พ.ศ.` · `20.00 น.` — grep TH-OR-01 ติดหมด แต่ถูกต้องแล้ว
ในคลังข้อมูล 1,134 hit **ไม่มี FP อักษรย่อสักตัว** (ทุกตัวตามด้วยเว้นวรรค/ขึ้นบรรทัด/จบข้อความ)
แต่ในไฟล์ docs ของ repo เจอทันที

**เป็น tell จริงเมื่อ:** จุดนั้นปิดประโยคไทยเต็ม ไม่ได้ห้อยท้ายอักษรย่อ

## 21. ตัวเลขวัดจริงใน docs และ commit

`แก้ UI ราว 50 จุด` · `709 บรรทัด` — `tells-en.md` คุ้มครองไว้ว่าเป็นของดี ไม่ใช่ความยาวเกิน
· หน่วยวัดในสตริง UI (`วันนี้ครบ 8 ชม. แล้ว`) ก็ห้ามแปลงเป็นคำ

**เป็น tell จริงเมื่อ:** ไม่มี — ห้ามแก้ทุกกรณี (TH-OR-03 ใช้กับเนื้อความบรรยายเท่านั้น)

## 22. `"` ที่คร่อม string ในโค้ด

`const label = "ยืนยัน"` · `{"title": "รายงาน"}` — **แก้แล้วโค้ดพัง**
TH-OR-04 ใช้กับไฟล์เนื้อหาเท่านั้น

**เป็น tell จริงเมื่อ:** ไม่มีในไฟล์โค้ด — ในไฟล์เนื้อหา (md, JSON เนื้อหา, CMS) เมื่อ `"`
คร่อมข้อความไทยที่ผู้อ่านเห็น

## 23. คอมมาคั่นตัวอย่างใน quote

`"เกลาคำหน้านี้", "ตัดสำนวน AI", "ยาวไป"` — เจ้าของ restore กลับเองหลัง AI ตัด
เป็นความชอบของเจ้าของที่บันทึกไว้ ไม่ใช่ข้อยกเว้นของกฎไหน (repo นี้ยังไม่มีกฎคอมมา)

**เป็น tell จริงเมื่อ:** ไม่มี — ลิสต์ตัวอย่างใน quote เก็บคอมมาไว้เสมอ

## 24. `บริษัทฯ` เป็นประธานซ้ำใน `formal`

ห้ามตัดด้วยกฎ TH-UI-06 · แต่ qualifier แบบ `ในมุมมองของบริษัทฯ` ยังตัดได้

**เป็น tell จริงเมื่อ:** อยู่นอก register `formal`

## 25. `—` เปล่าในช่องตัวเลขความกว้างคงที่

`0 / — หน้า` ที่ `—` ยืนแทน "ยังไม่รู้เพดาน" และมีข้อความข้าง ๆ อธิบายเหตุผลอยู่แล้ว
(`เลือกหมวดเพื่อดูจำนวนหน้าสูงสุด`) — ใส่คำแทนจะได้ `0 / ไม่ระบุ หน้า` ซึ่งอ่านไม่ออก
คลังข้อมูลที่ห้า: 2 จุดนี้รอดรอบกวาดที่ฆ่า em-dash 18 ตัวในไฟล์เดียวกัน

**เป็น tell จริงเมื่อ:** `—` ยืนแทนค่าในบรรทัดข้อความปกติ ไม่ใช่ในช่องตัวเลขที่ความกว้างตายตัว
และไม่มีข้อความอื่นบอกเหตุผลของความว่าง (TH-UI-03)

## 26. อักษรย่อไทยในสตริง UI — TH-OR-01 แม่นยำ 0% ใน register `ui`

คลังข้อมูลที่ห้า: `grep -nE '[ก-๙]\.'` บนสตริงที่ render จริง ได้ 13 hit **13/13 เป็นอักษรย่อ**
(ชื่อย่อสถาบัน/หน่วยงาน 8 แบบ · ชื่อย่อเดือน · หน่วยวัด `กก.` `ซม.` `ชม.`) มหัพภาคปิดประโยคไทย
**0 ครั้งใน 21 commit** — ป้ายสั้นภาษาไทยเต็มไปด้วยอักษรย่อ ไม่ใช่ประโยค กฎที่ว่าด้วยการปิดประโยค
จึงไม่มีอะไรให้จับ (ตรงข้ามกับคลังข้อมูลเนื้อหายาว ซึ่ง 1,134 hit เป็นของจริงหมด — ข้อ 20)

**เป็น tell จริงเมื่อ:** จุดนั้นปิดประโยคไทยเต็ม · ใน `ui` ให้ถือว่า base rate ~0 รันได้แต่อย่าคาดหวัง

## 27. em-dash ใน prose ไทยที่เจ้าของเขียนเอง (docs ในโปรเจกต์)

ข้อ 4 คุ้มครองแค่ prose **อังกฤษ** แต่ไฟล์ handoff / บันทึกงานภาษาไทยที่เจ้าของเขียนเองก็ใช้

## 28. ศัพท์เฉพาะที่ตัวคำเป็นอุปมาของภาษาต้นทางเอง

`กิ่ง` ใน "12 กิ่ง" ดูเหมือนอุปมาที่ผู้เขียนเติม แต่มาจาก 支 ใน `天干地支` ซึ่งคนจีนเปรียบเป็น
ก้านกับกิ่งของต้นไม้เองมาสามพันปี — L2 (TH-PR-12) ห้ามแตะคำกลุ่มนี้ เพราะแปลว่าเปลี่ยนศัพท์
ของศาสตร์นั้นทิ้ง เทียบได้กับข้อ 8

**แต่มีการบ้านสองข้อที่มาพร้อมกัน**

1. **ต้องนิยามตอนใช้ครั้งแรก** ในงานจริงคำนี้โผล่ 3 ครั้งก่อนถูกอธิบาย และย่อหน้าที่นิยามมันไว้
   ถูกตัดทิ้งตอนย่อบทความ ทำให้คำลอยทั้งโพสต์ — **ตัดเนื้อหาแล้วต้อง grep ศัพท์ทุกตัวที่ย่อหน้า
   ที่ถูกตัดเคยนิยามไว้** วิธีที่ทนการตัดที่สุดคือยัดนิยามลงในวงเล็บที่ตัวรายการเลย
   (`60 คู่ก้านกิ่งจีน (จีนเรียก 天干地支 …)`) เพราะวงเล็บไปไหนก็ไปกับคำ
2. **ต้องไม่ชนอุปมาของผู้เขียนเอง** งานเดียวกันใช้ภาพต้นไม้แทนเชื้อสายตำราด้วย (`ราก` `ลำต้น`
   `กิ่งของบาบิโลน`) ผู้อ่านจึงเจอ `กิ่ง` ครั้งแรกในความหมายเชื้อสาย แล้วอีก 29 บรรทัดต่อมาเจอ
   `60 กิ่งก้าน` ซึ่งเป็นคนละเรื่อง — แก้โดยย้ายอุปมา**ของผู้เขียน**ไปใช้คำอื่น (`กิ่ง` → `สาขา`)
   ไม่ใช่ย้ายศัพท์ของศาสตร์

**เป็น tell จริงเมื่อ:** ไม่มี — ห้ามเปลี่ยนตัวศัพท์ · แต่ถ้าใช้แล้วไม่นิยาม หรือชนกับอุปมาของ
ผู้เขียนเอง อันนั้นเป็นข้อบกพร่องที่ต้องแก้ (ที่โครง ไม่ใช่ที่ตัวคำ — TH-PR-15)

รอบนี้ไม่ใช่ความพลาดเดียว แต่เป็นการเทียบ AI-เกลา กับ เจ้าของ-เกลา บนเอกสารเดียวกัน
สิ่งที่ AI ทำไม่เป็นเลยและได้ขึ้นเป็นกฎใหม่:

| ที่ได้มา | กฎ |
|---|---|
| แก้คำเรียก 3 รอบไม่สำเร็จ เจ้าของเปลี่ยนโครงรอบเดียวจบ | TH-PR-15 (หมวด Q) |
| เจ้าของตัด `คนมักเข้าใจผิดว่า` · `ข้อนี้สำคัญที่สุด` | TH-PR-16 (หมวด R) |
| เจ้าของพิมพ์ `กฏ` และสะกด `แพตเทิร์น`/`แพทเทิร์น` สองแบบ | TH-OR-05, TH-OR-06 |
| เจ้าของกลับด้านประโยคนามยาวใน prose | D2 (ขยาย TH-UI-05 ออกจากสตริง UI) |

**ข้อสังเกตที่ควรจำ:** สองแถวล่างเป็นของที่**เจ้าของทำผิดเอง** ไม่ใช่ของที่เจ้าของแก้ให้ —
งานเกลาต้องตรวจทั้งของที่ AI เขียนและของที่คนเขียน กฎอักขรวิธีไม่ยกเว้นใคร

### 2026-07-30 — ไม่มีด่านข้ามเอกสาร พลาดสามครั้งในเซสชันเดียว (ปล่อยผ่าน)

`ก้านกิ่ง` เสียนิยามเพราะย่อหน้าที่อธิบายถูกตัด · `3 สาย` กลายเป็นเลขลอยหลังเปลี่ยนโครงลิสต์ ·
หัวข้อเลื่อนไปใช้คำพ้องความ ห่างจากย่อหน้าสรุปที่ประกาศศัพท์ไว้ 38 บรรทัด — สามครั้ง คลาสเดียวกัน
และทั้งสามครั้งด่านทุกด่านในไฟล์ขึ้นเขียวหมด

**ทำไมถึงพลาด:** ด่านทั้งหมดใน `SKILL.md` §2/§6 เป็นด่าน**ทีละบรรทัด** (grep pattern แล้วเปิดดู
บรรทัดนั้น) ไม่มีด่านไหนถือเอกสารทั้งฉบับไว้พร้อมกัน · รอบแรกแปะไป 2 ข้อแล้ว แต่ตั้งเงื่อนไขว่า
"ถ้ารอบนี้ตัดเนื้อหาออกด้วย" ซึ่งแคบเกินไป — ข้อที่สามเกิดจากการแก้คำเฉย ๆ ไม่ได้ตัดอะไรเลย

**กติกาใหม่:** ด่านข้ามเอกสารเป็นขั้น**บังคับทุกรอบ**ของงานเนื้อหายาว (`SKILL.md` §6) สามข้อคือ
ศัพท์ยังมีนิยาม · เลขยังนับตรงกับลิสต์ · ศัพท์ในย่อหน้าสรุปยังใช้คำเดิม · บทเรียนที่กว้างกว่านั้นคือ
**ด่านขึ้นเขียวทุกด่านไม่ได้แปลว่างานถูก ถ้าไม่มีด่านที่วัดสิ่งนั้น** — เหมือน entry 2026-07-29
เรื่องหมวด L ที่ grep ได้ 0 แล้วปิดด่าน

### 2026-07-30 — เส้นแบ่งว่าแก้เองตรงไหน เสนอตรงไหน (ข้อสังเกต ไม่ใช่ความพลาด)

เซสชันเดียวกันเป็นการเทียบ **เจ้าของเกลา** กับ **AI เกลา** บนเอกสารเดียวกันสองรอบ ผลไม่กระจาย
สุ่ม แต่แยกเป็นสองกองตามคลาสของการตัดสิน: ของที่**ตรวจได้**กับกฎภาษาหรือกับอีกส่วนของเอกสาร
AI ถูกเกือบทุกครั้ง · ของที่ต้อง**ตัดสินแทนคนอ่าน** เจ้าของถูกเกือบทุกครั้ง

เส้นแบ่งไม่ใช่ใหญ่กับเล็ก — `เสื้อคลุม` เป็นคำเดียวแต่อยู่กองขวา เพราะคำถามคือคนอ่านถอดรหัสออก
ไหม ไม่ใช่คำถามที่เปิดไฟล์แล้วตอบได้

**ที่เอาไปทำ:** ตาราง 2 กองพร้อมท่าที่ควรใช้ อยู่ใน `SKILL.md` §1 หัวข้อ "แก้เองตรงไหน เสนอตรงไหน"
ก่อนหน้านี้ §5 กับ §7 บอกว่าต้องเสนอไม่ใช่แก้เงียบ แต่ไม่ได้บอกว่า**คลาสไหน**ควรเสนอ ทำให้ที่ผ่านมา
สลับกันแบบไม่มีเกณฑ์

⚠️ **n = 1 เซสชัน** ยังไม่มี keep rate ห้ามอัปเป็นกฎ hard และห้ามใช้อ้างว่า "AI ตัดสินเรื่องคำได้
เจ้าของตัดสินเรื่องคนอ่าน" เป็นกฎทั่วไป จนกว่ามีรอบที่สองมายืนยัน

### 2026-07-30 — ด่าน TH-OR-05 จับ `ปรากฏ` ว่าสะกดผิด และ ⚠️ ของตัวเองบอกว่าไม่จับ (flag ผิด)

`grep -rnE "กฏ|…"` แมตช์อยู่ใน `ปรากฏ` และ `ปรากฏการณ์` เพราะ `ปรากฏ` สะกด ป-ร-า-ก-**ฏ**
ซึ่งเป็น ก ตามด้วย ฏ พอดี รันด่านนี้ทับไฟล์กฎของ repo เองได้ **7 บรรทัด** ที่ `ปรากฏ` เป็นตัวจุด
โดย 5 บรรทัดขึ้นแดงเพราะ `ปรากฏ` ล้วน ๆ (`tells-th.md` 272 · 394 · 411 · 530 · ไฟล์นี้ 308)
เป็น FP เต็มตัว ส่วนอีก 2 บรรทัดเป็นบรรทัดที่มี `กฏ` จริงปนอยู่ด้วย จึงขึ้นแดงอยู่แล้วไม่ว่าจะแก้หรือไม่

**ทำไมถึงพลาด:** ⚠️ ใต้โค้ดของ TH-OR-05 เขียนไว้ว่า `ปฏัก` `ปฏิบัติ` `ปรากฏ` ถูกกันแล้ว
ด้วยการ anchor เป็น ก + ฏ — เหตุผลนั้นถูกสำหรับสองคำแรก (ฏ ตามหลัง ป ไม่ใช่ ก) แต่ผิดสำหรับ
คำที่สาม โน้ตจึงไป**การันตี**คำเดียวที่ตัวเองกันไม่ได้ และเพราะโน้ตยืนยันว่า "ไม่มี false positive
ให้ต้องชั่งใจ" คนรันด่านจึงไม่มีเหตุให้ไปเปิดดูว่า hit นั้นคืออะไร

**กติกาใหม่:** pattern ที่เป็น**ลำดับอักษรสองตัว** ต้องเทียบกับคำที่มีลำดับนั้นอยู่ในตัวก่อนขึ้นเป็น
`hard` ไม่ใช่เทียบแค่คำที่มีตัวอักษรนั้น · และ**ข้ออ้างว่า "หมวดนี้ไม่มี FP" ต้องมีผลรันจริงรองรับ**
เหมือนที่ `hard` ต้องมี keep rate — ของจริงคือรันด่านทับ repo ตัวเองแล้วอ่านผลกลับทีละบรรทัด
ซึ่งเป็นบทเรียนเดียวกับ entry 2026-07-29 (grep หมวด L ได้ 0 แล้วปิดด่าน) และ 2026-07-30
(ด่านขึ้นเขียวทุกด่านไม่ได้แปลว่างานถูก ถ้าไม่มีด่านที่วัดสิ่งนั้น)

### 2026-07-30 — คำสั่งเกลาที่ต้องแก้ที่ logic ไม่ใช่ที่คำ (ช่องโหว่ของ §5)

`SKILL.md` §5 เขียนว่า **ห้ามแตะ logic** แล้วเปิดข้อยกเว้นไว้สองข้อ (conditional render
ระดับบรรทัด TH-UI-03 · ระดับ section TH-UI-09) แต่ในรอบที่เจ้าของเปิดหน้าจอจริงแล้วคลิกสั่งแก้
ทีละ element คำสั่งที่ออกมาพันกับงานคำตั้งแต่ต้น:

| ที่เจ้าของสั่ง | จริง ๆ คืออะไร |
|---|---|
| `ไม่เอา ui ซ้ำซ้อน` (ช่องพิมพ์ปีกับล้อเลือกปี ทำงานเดียวกัน) | ตัด control ทิ้ง ไม่ใช่ตัดคำ |
| `ถ้าไม่ชง ก็ไม่ต้องพยายามขายดีกว่า` | conditional render ทั้ง section ตามผลคำนวณ |
| `ตรงนี้ขึ้นกับแพ็กที่เลือก` | เปลี่ยนข้อความตายตัวเป็นค่าที่ derive จาก state |
| `ให้ auto select ไว้ ขึ้น chip ว่าแนะนำ` | เปลี่ยน default แล้วเพิ่มสถานะ selected |

**ทำไมถึงเป็นช่องโหว่:** §5 ตอบได้แค่ทำหรือไม่ทำ ทั้งที่ของจริงเจ้าของสั่งมาแล้ว คำถามที่ยังไม่มี
คำตอบคือ **ทำแล้วรายงานยังไงให้เจ้าของเห็นว่าอันนี้ไม่ใช่แค่คำ** และผลข้างเคียงของงานกลุ่มนี้
ไม่ได้อยู่ในคำ — ของจริงในรอบนั้น: เปลี่ยนช่องจังหวัดจากพิมพ์เองเป็นเลือกจากรายการ ทำให้เงื่อนไข
validation ที่อ้างช่องเดิมหลุด ปุ่มจ่ายเงินกดได้ทั้งที่กรอกไม่ครบ

**กติกาใหม่:** ทำให้ตามที่สั่ง แล้วแยกแถวนั้นในรายงานว่าไม่ใช่งานคำ พร้อมบอกผลข้างเคียงที่ตามมา
และสิ่งที่แก้ตาม — ท่านี้ใช้จริงแล้วในรอบนั้นและเจ้าของรับได้

**ที่เอาไปทำ:** กองที่สามในตาราง `SKILL.md` §1 (แถวอยู่ที่นั่นแถวเดียว ไม่คัดลอกมาไว้ที่นี่)
· §5 บรรทัด logic ชี้ไปที่กองนั้นแล้วว่าคำสั่งของเจ้าของไม่ได้อยู่ใต้ข้อห้ามข้อนั้น

⚠️ **n = 1 รอบ และเป็นรอบที่เจ้าของนั่งดูอยู่ตลอด** ในงานเกลาที่เจ้าของไม่ได้อยู่ด้วย กองนี้
ยังต้องถามก่อนตามเดิม

### 2026-07-30 — คลังข้อมูลที่เจ็ด: เจ้าของสั่งแก้สดบนหน้าจอ (ข้อสังเกต ไม่ใช่ความพลาด)

ต่างจากคลังข้อมูลก่อนหน้าตรงที่ **ไม่มีใครอ่าน diff เลย** เจ้าของตัดสินจากสิ่งที่เห็นบนจอ
